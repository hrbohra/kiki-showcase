Kiki · the AI

It writes from the facts. It will sound like Kiki.

Every introduction on Kiki is written by a language model from the trust graph, never from its imagination. That part runs today. This page covers it and the part that comes next: giving it Kiki's own voice, learned from roughly ten thousand real conversations, without letting those conversations become anything but a tone of voice. The voice engine, Voiceprint, is built, published and measured. Below are the architecture, the system as it stands, the decisions and why, the scope it will never leave, and the steps to run it on Kiki's data.

00 · The choiceWhat Kiki needs from a voice, and why this way.

Kiki's introductions work because a stranger trusts them. Once the AI writes them, the tone becomes part of that trust. It has to sound like Kiki, not like a chatbot, and it can never say more than the graph can prove. The raw material is about ten thousand conversations between Kiki's team and its members, and those are private.

So the question was never "can a model imitate Kiki?". Several methods can. It was which method gives Kiki's voice without costing members' privacy or the product's honesty.

What Kiki needs

  1. Sound like KikiThe habits that set Kiki apart from other hosts and brands, not "friendly".
  2. Keep to the factsThe voice may change how something is said, never what. Content comes only from the trust graph.
  3. Keep members' words privateConversations are never quoted, never sent raw to a provider, and never turned into model knowledge.
  4. Let the team see and own itA voice the team can read, argue with and edit, not a black box.
  5. Be provableA test that shows the voice is really Kiki's, on conversations it has never seen.
  6. Stay light and portableCheap to run, and free to switch AI models without redoing the work.

Why this one

  • It is the only option that meets all six needs. Every alternative trades one away: fine-tuning gives up privacy and honesty, retrieval quotes members, the hand-written prompt can't prove anything, and pasting conversations sends members' words out on every call.
  • Its one weakness is covered. A prompt imitates less deeply than a fine-tuned model. Voiceprint measures that gap: with the pack, replies score level with the brand's real ones (chapter 04). It also exports style-only fine-tuning files, so if the gap ever matters, the stronger option is one step away, using data already cleaned of facts and names.
  • It starts from what Kiki runs today. Kiki already has a voice port holding a hand-written prompt. Voiceprint replaces that prompt with a measured one. Nothing else in the AI layer changes, so the upgrade is one line and reversible.

01 · The system todayOne contract, one runner, and it never breaks or lies.

Kiki's AI jobs are well defined: one call over facts the product already holds. So there is no agent framework. There is a small contract of my own. Each AI feature is a task: the typed facts it may use, a prompt, a guard that accepts or rejects the answer, and a deterministic twin that says the same true thing without a model. All four are pure functions in @kiki/domain, versioned and unit-tested.

The API calls a model in exactly one place, the AiRunner. Every task inherits the same fallback ladder, so a demo can never show a broken box, and every answer says which rung produced it.

02 · The voice engineMeasure how Kiki writes, prove each habit, then hand it to the model.

Giving a model "Kiki's voice" usually means someone writes "be warm and friendly" into a prompt. That describes every brand, so it describes none. Voiceprint works from evidence instead. It reads the conversations, measures about 155 properties of every message, finds where Kiki differs from comparable brands, turns each difference into a plain-language rule, and keeps a rule only if it holds on conversations it has never seen.

What comes out is a small set of files. @kiki/voice loads them with one call, and the rest of the AI layer does not change.

03 · DecisionsEach one made for Kiki's constraints, with what was rejected.

All 53 are recorded with their reasons in the build log. These are the ones that shape Kiki.

  • The conversations shape tone and nothing else. Never facts, matching, ranking or search. The content of every introduction still comes only from the trust graph.Instead of fine-tuning on members' messages, which would turn private conversations into model knowledge.
  • Kiki is compared with other brands, never with its members. Public replies from comparable hospitality, travel and community accounts are the reference. Members' messages stay in only as context: what Kiki was replying to.Instead of Kiki vs its own members, which measures "company vs customer", not voice. I caught exactly this mistake in my own evaluation and corrected it.
  • Measure first; the frontier model reads a compressed brief. The statistics and a few hundred anonymised messages cost a few thousand tokens, and every claim carries a number.Instead of pasting the corpus into a model: about 30× the tokens, private text leaving the machine, and impressions nobody can check.
  • A rule is kept only if it is distinctive on unseen conversations. A blind judge labels held-out messages from Kiki and from the reference, shuffled together, and the difference must pass a one-sided Fisher exact test.Instead of trusting the model's first draft of rules. On a control corpus it proposed five plausible rules that were equally true of everyone, and the check rejected all five.
  • Style-only rules for Kiki. Some verified habits change what is said ("move this to a private link", "promise a follow-up"). Kiki's content must come only from facts, so only style-only rules go into Kiki's pack.Instead of shipping every verified rule, which let the voice add claims the graph never made.
  • The scorer runs in the app with no model. A logistic model over exact surface features, generated as dependency-free TypeScript and tested to match the Python version to 1e-6.Instead of an embedding model in the request path: slower, costlier, and a second thing to host.
  • Built for the machine it runs on. One Windows laptop with an 8 GB GPU. Models load per stage and are released, every stage is checkpointed, and a low-power mode with a thermal guard keeps the laptop usable and below its throttle point.Instead of assuming a cloud GPU. Kiki's team can run it on an ordinary laptop, and the data never needs to leave it.

04 · EvidenceTested where the right answer is known, then on real brands.

Kiki's conversations are private, so every test uses public or synthetic data with the same shape: one account answering many different people. The closest public match is ten brands' customer-support replies on Twitter.

The first test plants six habits in a synthetic host's replies and asks whether the engine finds them. It finds all six, and on a control with nothing planted it finds nothing.

05 · ScopeWhat it does for Kiki, and what it will never do.

The boundary is the product. Members wrote to Kiki to arrange stays, not to train a model, so the line sits where their trust needs it.

In scope
  • Tone: how an introduction or a draft sounds (rhythm, warmth, formality, habits) learned from Kiki's own replies.
  • A yardstick: "would Kiki have said it like this?", scored in-app, so the best of several drafts can be picked.
  • A voice guide for people: VOICE.md, every rule with its evidence, which the team can read, edit and veto.
  • Optional fine-tuning files (style-only pairs) if prompting ever falls short.
Out of scope, always
  • Facts. Who someone is, what they did, and who vouches for whom come only from the trust graph.
  • Matching, ranking, search or any decision about a member.
  • Quoting members. No output may contain a phrase found in fewer than three conversations; a leak fails the run.
  • Acting. The AI still only proposes text, and a person sends it.

06 · How to run itFrom Kiki's export to Kiki's voice, on one laptop.

Seven steps, each reversible. Nothing reaches production until a person has read the voice guide and a held-out test has passed.

Before step 1: agree the lawful basis for using the conversations for tone, and keep the export in an access-controlled folder. The default tier sends no raw text anywhere.
  1. Export the conversations

    Instagram → Settings → Download your information → Messages, JSON format. Voiceprint reads the folder directly and repairs Instagram's broken emoji encoding.

  2. Install and check the machine
    # Python 3.11+, an NVIDIA GPU if available (CPU works, slower)
git clone https://github.com/hrbohra/voiceprint && cd voiceprint
python -m venv .venv && .venv/Scripts/activate
pip install -e ".[gpu,anthropic]"
python -m spacy download en_core_web_trf
voiceprint doctor          # GPU, spaCy, which providers have keys
  3. Look at what it sees
    voiceprint inspect instagram_export/
# → turns, conversations, and each speaker's name (the Kiki account's is the target)
  4. Add the reference brands

    Collect a few hundred public replies each from comparable hospitality, travel and community accounts, as JSON Lines (speaker, doc_id, text), and put them alongside Kiki's conversations in one file.

  5. Extract the voice
    export ANTHROPIC_API_KEY=…        # Claude does the reading and the blind checking
export VOICEPRINT_LOW_POWER=1    # idle priority + thermal guard: the laptop stays usable
voiceprint extract kiki_and_reference.jsonl \
  -s "Kiki" -r "BrandA" -r "BrandB" -r "BrandC" \
  -o voice/

    Every stage checkpoints, so a restart or a sleeping laptop loses at most a few minutes. The LLM stages need about a dozen calls under a hard spending cap (£20 by default), and every call is cached.

  6. Read and edit the voice guide

    Open voice/VOICE.md. Every rule shows how often Kiki follows it compared with the reference, and its p-value. Delete any rule that carries content (a promise, a redirect) or that the team doesn't recognise as Kiki.

  7. Plug it in, then gate it
    // apps/api/src/ai/ai.module.ts
import { fromVoiceprint } from '@kiki/voice';
const voice = fromVoiceprint({ tonePack, voiceJson });
{ provide: VOICE_PROVIDER, useFactory: () => voice.provider }
// optional: write 3 drafts, keep voice.pickMostOnVoice(drafts)

    Then run the fidelity check on held-out conversations. It passes when the on-voice score approaches Kiki's real replies and the voiced drafts still say only what the plain ones said.

07 · Honest limitsWhat the numbers don't show yet.

  • Rare habits need more checking. With 48 judged messages per side, a habit must appear in roughly one Kiki message in ten to prove itself. True habits rarer than that are dropped, not faked. Kiki's volume allows a larger check.
  • The style judge in the published tests was not independent. With no API key available during the build, I answered the frontier stages myself inside a Claude Code session, including the style judge. That is labelled everywhere, and the headline numbers come from model-free measures instead.
  • English only. Non-English turns are detected and set aside.
  • Style-only tagging is next. Rules are currently checked for content by reading VOICE.md. The planned automatic check tests whether applying a rule changes what a reply entails.

Informed by Anthropic's Building effective agents (workflows before agents), the OWASP Top 10 for LLM applications (2025), and the stylometry literature behind the features: Language Style Matching, the Heylighen–Dewaele formality score, and Monroe et al.'s log-odds keyness.
